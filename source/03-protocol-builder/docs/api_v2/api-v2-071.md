# api-v2-071 — RuntimeControllerEvents.ProgressChanged(value)

| Field | Value |
| --- | --- |
| **Method** | `RuntimeControllerEvents.ProgressChanged(value)` |
| **Priority** | medium |
| **Workflow** | Offline mock runtime / `generate --progress/--event-log` |

## Improvement

Push-based init/method progress (0–100) for CLI heartbeats, stall/timeout detection, and structured telemetry during long `InitializeInstrument` or `PrepareMethod` runs instead of polling `GetProgress` / `GetProgressInitialization`.

## Implementation

- `fluent_pipeline/api_v2/progress.py` — `RuntimeProgressTracker.notify_progress_changed()` records push events with source `ProgressChanged` and emits `progress_event()` payloads for `--event-log`.
- `fluent_pipeline/api_v2/run_control.py` — `build_progress_tracker()` wires mock progress into offline stepped waits.
- `fluent_pipeline/api_v2/runtime_events.py` — `RuntimeEventCollector.on_progress_changed()` forwards to optional tracker callbacks.
- Offline reports may include `details.progress_events` when event logging is enabled.

## Usage

Prefer subscribing to `ProgressChanged` (or the mock runtime equivalent) over polling alone. Poll `GetProgress()` remains a fallback when events are unavailable offline.
