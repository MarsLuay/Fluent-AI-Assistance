# Architecture

fluentcoder separates the system into three layers, each with one clear job.

```
[Python class hierarchy]   ← BEHAVIOR + invariants (~10 classes)
       ▲
       │  fixed by author OR dispatched by inferred category
       │
[SQL catalog index]        ← IDENTITY + file pointer (one row per ObjectName)
       ▲                     stored at fluentcoder/catalog/install_index.db
       │  built once on first import; refreshable via CLI
       │
[FluentControl install XML]   ← FACTS (geometry, sites, occupancy)
   C:\ProgramData\Tecan\VisionX\Database\SystemSpecific\Worktable\
```

1. **Python class** — `Plate`, `Trough`, `TipBox`, `MagnetRack`, etc. declare
   *behavior*. A `Plate` knows pipetting it is auto-parallel over a well grid;
   a `MagnetRack` declares "labware stacked on me triggers
   `is_magnetized=True`." Class-level constants describe *taxonomic shape*
   only (Plate96 → 8×12 wells); per-catalog facts come from the lower layers.

2. **SQL row** — links a catalog name (e.g. `"96 Well Flat"`) to a file path
   and an inferred category. Built by walking the FluentControl install once.

3. **XML on disk** — the FluentControl install carries the source-of-truth
   for geometry (well grid, mm dimensions, site offsets, grip modes). Read on
   demand by the .xcmp parser; cached for the process lifetime.

## Why three layers

- The same Python *class* (`Plate96`) covers many real catalog entries
  (96 Well Flat, AB-2225, Greiner 96 V-bottom…) because they share *behavior*
  even when their dimensions differ. Hardcoding dimensions would force
  one-class-per-catalog-entry; with this split, 629 catalog rows resolve
  through ~10 classes.
- The FluentControl install changes per machine. Indexing the install
  removes the need for fluentcoder to ship a static catalog, and lets users
  drop a new component into the install and have fluentcoder pick it up via
  `fluentcoder catalog refresh`.
- The XML stays the source of truth — fluentcoder never duplicates facts that
  already live in `.xcmp`.

## The data plane

```
[ author writes Python ]
       │
       │  Worktable / Labware / Reagent / Head methods
       │  (each method emits one IR step; nothing else)
       ▼
[ Protocol IR list ]                         ← list of pydantic Step objects
       │
       ├── wt.compile(out)  ──▶  XML renderer  ──▶  .xscr (XML for FluentControl)
       │
       └── wt.simulate()    ──▶  Simulator (walks IR, builds twin, snapshots per step)
                                              │
                                              ▼
                                  wt.snapshots[i]   (queryable per-step state)
```

Two key separations:

1. **Authoring vs. simulation are decoupled.** Author method calls produce
   IR; the IR is the only input the simulator reads. The simulator can be
   pointed at any IR — including IR loaded from disk or generated by a
   third party. State observed in `wt.snapshots[...]` is reconstructed
   solely from the IR.

2. **Authoring vs. compilation are decoupled.** `compile()` builds a
   `Protocol` IR object and hands it to the renderer; nothing about
   authoring touches the XML. The renderer descends from the earlier
   project-owned fluentdsl implementation and is maintained as package-local
   code so byte-equal parity is achievable where both support the same
   protocol.

## Resolution flow — `Plate96('Source', catalog='96 Well Flat')`

1. Class fixes the *behavioral* family (plate) and the *taxonomic grid*
   (`Plate96` → 8×12).
2. `index_exists()` is True (catalog index built); the constructor demands
   a `catalog=` argument.
3. `resolve_by_name('96 Well Flat')` returns a `CatalogEntry` with the path
   to the .xcmp.
4. `load_xcmp(...)` parses the .xcmp into typed dataclasses.
5. `_populate_from_catalog(...)` walks the `Pipettable` block to build 96
   `Well` objects with cavity-derived max volumes (~392 µL) and per-well
   mm positions; stores `dim_mm`, `site_offsets_mm`, `catalog_name`.

When the index is empty (CI / dev box), step 2 fails and the constructor
falls into the offline-synthesis path: it builds 8×12 generic wells with
a family default max-volume (350 µL for `Plate96`) and emits a one-shot
`CatalogIndexMissing` warning. mm fields stay `None`.

## Resolution flow — `Worktable.from_workspace('780_Empty')`

1. Catalog index must exist (raises `MissingSimValueError` if not).
2. `resolve_workspace_by_name(...)` returns a `WorkspaceEntry` pointing at
   the .xwsp.
3. `load_xwsp(...)` parses the workspace's site tree into:
   - `available_sites` — every visited site frame as `(site_path, base_loc)`
   - `occupants` — sites that already carry a labware
4. The Worktable's `valid_slots` whitelist becomes
   `{(base_loc, site_index + 1) for every available site}` — XWSP indices
   are 0-based, FluentControl positions are 1-based, so we translate at the
   boundary.
5. With `auto_place=True` (default), each occupant's catalog name is
   resolved via `resolve_by_name`, dispatched to the right Python class via
   `CATEGORY_TO_CLASS[catalog_entry.category]`, instantiated, and `place()`-d.

After this, `wt.place(...)` raises `InvalidSlotError` for any slot not in
`valid_slots`.

## Module map and dependencies

```
fluentcoder/__init__.py
   │
   ├── catalog.ensure_index()                     ← runs on first import
   │
   ├── reagent.Reagent
   ├── worktable.Worktable
   │      ├── heads.MCA96Head        (mca96 attr)
   │      ├── gripper.Gripper        (gripper attr)
   │      └── simulator.Simulator    (lazy import in simulate())
   ├── labware.{Plate96, Plate384, MCA100Box, MagnetRack, …}
   │      └── catalog.{index_exists, resolve_by_name, load_xcmp}
   ├── compiler.render_protocol     ← drives the .xscr renderer
   └── simulator.{Simulator, Snapshot, *Error}

fluentcoder/catalog/
   ├── catalog.py        ← SQL queries (resolve_by_name / find / list)
   ├── indexer.py        ← walk install, infer category, write rows
   ├── inference.py      ← FunctionalGroup + name → category
   ├── xcmp.py           ← .xcmp / .xwsp / .xsit typed parser
   ├── database.py       ← legacy recipe database and lookup helpers
   ├── fc_install.py     ← bridge to fluentcontrol_core (rewrite_checksum etc.)
   └── install_index.db  ← built artifact (one row per ObjectName)

fluentcoder/labware/
   ├── base.py           ← Labware + Layer + Well + offline synthesis path
   ├── plates.py         ← Plate, Plate96, Plate96Deep, Plate384
   ├── troughs.py        ← Trough, Trough25mL, Trough100mL, Waste
   ├── tipboxes.py       ← TipBox, MCA*Box, FCA*Box
   ├── magnet.py         ← MagnetRack
   ├── adapters.py       ← Adapter, EvaAdapter
   ├── tuberack.py       ← TubeRack
   └── deckitems.py      ← WashStation, WasteChute, Hotel, FixedDeck

fluentcoder/heads/
   └── mca96.py          ← MCA96Head + Tip dataclass

fluentcoder/simulator/
   ├── walk.py           ← IR walker, dispatch, layered aspirate/dispense math
   ├── snapshots.py      ← deepcopy-frozen Snapshot per step
   └── invariants.py     ← physical-invariant exception hierarchy

fluentcoder/ir/
   └── schema.py         ← Pydantic Protocol + Step types

fluentcoder/compiler/
   └── renderer.py       ← Tecan XML renderer

fluentcoder/_assets/
   ├── templates/*.xml          ← XML wrapping templates
   ├── reference/*.yaml,*.txt   ← commands.yaml / labware.yaml / liquid_classes.yaml / locations.txt
   └── config/generation.yaml   ← renderer config
```

## Implementation provenance

The IR schema, XML renderer, FluentControl install bundle reader, and the
templates / reference / config under `_assets/` descend from the earlier
project-owned fluentdsl implementation. They are now maintained as
package-local fluentcoder code.

Tecan/FluentControl-facing reference material is documented separately in
`NOTICE.md` and `REVIEW_NOTES.md`, because command XML, catalog-derived data,
workspace names, and generated `.xscr` samples need a more conservative
provenance audit than ordinary Python source.

See [docs/development.md](development.md) for repo layout, test strategy,
and known gaps.
